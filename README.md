## 고민/어려움 1: 입출력은 기능인가 비기능인가? <br>


>문제 상황
>- 입출력 구현 방법이 기능인지 비기능인지 구분이 어려웠다
>- "구분자로 입력받는다"와 "파싱 방법"의 차이가 모호했다
>
>나의 행동
>- 입출력이 없으면 동작 자체가 안되니까 입력/비즈니스/출력으로 3분할 했다. 
>
>결과
>- 일단 정리는 완료했다.
>- 근데 확신하기 어렵다.
>
>받고 싶은 피드백
>- 입출력을 어떻게 구현하는지도 구현에 넣어야하는가? 
>  이거를 고민하는 이유가, 입출력에서 제대로 팟싱이 안되면 애플리케이션이 안돌아가기 때문이다. 

### 나의 문제

>내가 부족한 것은 기능/비기능을 구분 짓는 명확한 기준이 없다.
>- 나는 '동작에 필요하면 -> 기능'을 썼었는데, 이 기준이 너무 넓다는 피드백을 받았다.
>  예를들어 DB 연결도 없으면 안돌아가고, 
>  네트워크도 없으면 안 돌아가고,
>  로깅도 없으면 디버깅이 안 되니까 
>  나는 이럴때 '전부 기능'으로 간주하는 경향이 있다.

### LLM 피드백: 아래와 같은 기준을 추가하여 명확히 할 필요가 있다.

> '기능 요구사항'은 고객이나 사용자가 원하는 것
> '비기능 요구사항'은 개발자가 선택하는 것 

### 연습1) 피드백 적용 연습
>>우테코 요구사항: "쉼표(,) 또는 콜론(:)을 구분자로 가지는 문자열을 전달하는 경우..."라고 명시되어 있다. <br>
> 
> 사용자의 문제: 구분자(쉼표,클론)로 숫자를 구분지어 입력하는 것<br>

> 
> 추가적으로 개발자의 문제(비기능)은 대체 가능성이라는 성질이 있는 것 같다. <br>
> 구분자가 쉼표,클론 말고 다른거면 요구사항 위반이다.  하지만 구분지어 입력받는 방법은 다른 걸로 대체될수 있다.

> - 4번은 사용자가 입력에서 고민하는 문제이기 때문에 기능이다.

## 고민/어려움 2:  예외처리는 최소 동작 애플리케이션에 포함 되는가?

>문제 상황
>- 예외처리가 명시적으로 적힌 요구사항인데 MVP에 포함인지 기준이 안선다. 
>  해피케이스만 생각하면 일단 앱이 돌아가기 때문이다. 예외처리까지 MVP에 포함시켜야하는가?
>
>나의 행동
>- 예외처리를 기능 요구사항에 포함
>- 하지만 구현 순서에 대한 확신이 없다.
>
>결과
>- 일단 MVP에 예외처리를 넣었다.
>- MVP 범위가 모호해졌다.
>
>받고 싶은 피드백
>- MVP는 happy case만 고려하나?
>- 나는 요구사항을 기능/비기능으로 나눈게 맞는가? 
>  맞다면 나는 기능/비기능을 어떻게 더 잘 나눌 수있지?


### LLM 피드백
> 나는 MVP를 하나의 개념으로만 보고 있는데, 사실은 두 개념이 존재한다고 한다.
> - 학습용 MVP
> - 출시용 MVP
> 
> 나는 "예외처리도 요구사항인데 MVP에 안 넣으면 이상하지 않나?" 라고 혼란스러워 했었다.
> 왜 혼란스러웠는지 생각해봤는데, 예외처리를 안해도 일단 동작은 하니까 비즈니스는 만족해서 MVP인 것 같은데 요구사항을 만족 안하니까 실패인건가? 딜레마가 왔던 것 같다.
>>즉, 나는 완전한 미션 구현을 고려했기 때문에 기능 요구사항으로 본 것이다.
> 
> 한편, LLM은 예외처리도 기능/비기능 2가지로 나뉜다고 한다.
> > 예를들어, "사용자가 잘못된 값을 입력할 경우 IllegalArgumentException을 발생 시킨 후 애플리케이션은 종료되어야 한다"라고 나와 있다. 
> 
> 기능:
> 
> "잘못된 값을 거부한다"는 기능이다. 이것은 비즈니스 룰이다. 계산기는 양수만 받겠다는 정책이고, 고객이 원하는 것이다. 만약 음수를 받아들인다면 요구사항 위반이다.
> 
> 비기능: 
> 
> "IllegalArgumentException을 던진다"는 비기능이다. 이것은 구현 방법이다. 개발자가 선택하는 것이기에 런타임을 던져도 되고 커스텀 예외를 만들어도 된다.
> 어떤 방법을 써도 "잘못된 값을 거부한다"는 기능은 만족하기 때문이다.
>
### 다음에는 이렇게 한번 시도해보려고 한다.
> 부족했던점:<br> 
나는 예외처리를 기능으로 처리하지 못했다. 왜냐하면 나는 '사용자의 문제(비기능의 정의)'라고 생각지 못했기 때문이다.
> 하지만 사용자는 '무엇을 거부할지, 안해야할지' 관심 있다. 예를들면 어떤 것들을 입력할 수 있지? 양수구나. 이런 것들.
> 
> 다음에는 이렇게 한번 시도해보려고 한다.
> 
> 기능의 기준을 '사용자의 문제' 해결에 두는 대신, '사용자가 무엇에 관심 있어 하는지', '무엇을 해야 하는지', '무엇을 해서는 안 되는지'라는 세 가지 질문으로 요구사항을 필터링하는 것이다.
> 
> 이를 통해 앞으로 새로운 요구사항을 마주했을 때, 그것이 기능적인지 비기능적인지 명확히 나누는 기준으로 삼을 계획이다.

## 문제 3: 내가 작성한 TodoList는 개발자가 무엇부터 개발하면 좋을지 불명확하다.

>문제 상황
>- 기능요구사항으로 부터 ToDoList를 작성해야 한다.
>
>나의 행동
>- 시스템은 What 무엇을 하면 되는가 행동 중심으로 정리했다.
>- 하지만 구현 순서에 대한 확신이 없다.
>
>결과
>- TodoList를 보고 개발자가 바로 개발하기엔 우선순위 불명확하다.
>
>받고 싶은 피드백
>- 어떻게 하면 개발자가 바로 행동으로 옮길 수 있는 TodoList를 만들 수 있을까?


### LLM 피드백
> 나의 부족한점: "행동 가능한 수준"의 기준이 부족하다.
> 
> 나는 What(무엇을) 할지는 잘 적었다. 하지만 "얼마나 작게?"에 대한 기준이 없어서 나의 TodoList는 개발자 입장에서 추상적이다.

### 좋은 TodoList에 대한 고찰
> 좋은 TodoList는 어떠한 개발자가 와도 똑같이 '무엇을''어떻게' 
> 
> 오류가 많은 내 ToDoList
> 
> 1. 나는 구성자를 기준으로 숫자들을 추출해야 한다고 적어놨다. 지금 당장 이것을 구현하려면 무엇을 해야할까? 기본구분자 먼저? 커스텀먼저?
 둘다 한번에? 
> 2. 내가 적어놓은 것 중에 '숫자들을 더한다.'라는 항목이 있다. 이게 5분안에 구현 가능한가? 어떤 숫자들? 몇 개? 예외? 불명확하기 때문에 고민을 할 것이고 바로 개발로 행동이 안옮겨질 것 같다. 
> 
> 나쁜 ToDoList의 특징
> 1. 추상적이다.
> 2. 순서가 없다.
> 3. 완료 기준이 없다.
> 4. 시간관리가 어렵다.
> 
> 좋은 ToDoList의 특징
> 1. 항목을 보는 순간 바로 행동 가능하다.
>    - 그러기 위해선 입력과 기대값이 명확할 필요가 있다.
>    - ex. "1,2,3"을 입력하면 6이 나와야한다.
> 2. 위에서 아래로 순서대로 하면 자연스럽게 완성된다. 
>    - B를 하려면 A가 필요하다면 A가 B보다 위에 있어야한다.
>    - ex. "쉼표로 분리 → 더하기 → 콜론 추가 → 커스텀 구분자 추가 → 예외 처리" 순서
> 3. 완료 기준이 명확하다.
>    - 실행이 된다. 또는 테스트가 돌아간다. 이렇게 정할 수 있는데 핵심은 "이 정도면 됐나?" 고민이 없게 하는 것이다. 
> 4. 모든 항목이 비슷한 크기여야 한다. 
>    - 각 항목이 5분~10분 정도 걸린다면 크기를 예측할 수 있으니 시간관리를 할 수 있고, 진행 상황 파악하기 쉽다.
>
> 그러면 ToDoList의 본질을 이렇게 정의할 수 있겠다
>  -  막연한 생각을 '지금 당장 할 수 있는' 구체적인 행동으로 바꾸고, 필요한 의사결정을 미리 해두는 것

#### 1. 기능/비기능 분리
> 작업 방법:
> 
> 요구사항 문서를 한 문장씩 읽으면서 질문한다.
> - "이것은 고객이 원하는 것인가? -> 기능 요구사항
> - "개발자가 선택하는 것인가? -> 비기능 요구사항"
> 
> 기능 요구사항을 입력/처리/출력으로 구조화한다.

#### 2. 기능 요구사항으로 거친 초안 작성
> 목표: Step 1에서 정리한 기능 요구사항만 보고 TodoList의 거친 초안을 작성한다. 비기능은 아직 보지 않는다.
>
> 작업 방법: 기능 요구사항을 읽으면서 "이것을 구현하려면 뭘 만들어야 하지?"라고 생각한다. 떠오르는 것들을 그냥 적어본다. 추상적이어도 좋다. 순서가 이상해도 좋다. 즉, 완벽을 추구하지 않는다.

#### 3. 순서 정렬
> 목표: Step 2에서 작성한 항목들의 순서를 정렬한다. 의존성을 고려한다. 그 다음에 쉬운 것부터 어려운 것 순서로 정렬한다.
>
> 작업 방법:
>    1. 항목들을 보면서 "A가 있어야 B를 할 수 있나?"라고 질문해본다. 
>    2. 그렇다면 A를 B보다 위에 놓는다.
>    3. "A와 B 중에 뭐가 더 쉽나?"라고 질문해본다.
>    4. A가 더 쉽다면 A를 먼저 놓는다.

#### 4. 입력과 기댓값 정의
>  목표: Step 3에서 정렬한 항목들을 구체적으로 (입력/기댓값)으로 바꿔본다.
>
>  작업 방법: 
> 1. 각 항목을 보면서 "이것을 어떻게 완료라고 정의하지?"라고 질문해본다. 입력과 기댓값을 정의해본다.
> 2. 한 항목이 여러 테스크로 쪼개 진다면, 그래도 모두 적는다.

#### 5. MVP 도출하기
> 목표: Step 4에서 만든 투두리스트 단위들 중에서 어디까지가 MVP인지 표시한다. (가장 핵심적인 것만 MVP로 표시)
>
> 작업 방법
> 1. 작업 단위들을 위에서 아래로 보면서 "이것 없으면 프로그램이 동작 안 하나?"라고 질문해본다. 그렇다면 MVP다.
> 2. "이것은 확장 기능인가?"라고 질문해본다. 그렇다면 MVP가 아니다.
> 3. 그 결과 MVP 와 기능확장 2가지로 나뉜다. 

#### 6. 비기능 요구사항 추가하기
> 비기능 요구사항은 기능 개발하면서 동시에 구현해도 좋다.
> 
> ex
> 1. Console.readLine()으로 입력 받기
> 2. "덧셈할 문자열을 입력해 주세요." 출력
> 3. "결과 : 6" 형식으로 출력

#### 7. 예외 처리
> 예외 처리도 추가한다. 예외 처리는 기능 요구사항에 있었지만, MVP에는 넣지 않았다. 이제 추가한다.
> 
> ex
> - 음수 입력시 예외<br>
    입력: "-1,2,3"<br>
    기대: IllegalArgumentException("[ERROR] ...")
